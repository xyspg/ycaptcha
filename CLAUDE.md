# yCAPTCHA

@AGENTS.md


Custom image-based CAPTCHA platform. Site owners create puzzles, embed widget via iframe, verify tokens server-side.


## Tech Stack

- Next.js 16 (App Router) + TypeScript
- PostgreSQL (Neon) + Drizzle ORM
- better-auth (email+password, GitHub OAuth, passkey)
- Tailwind CSS + shadcn/ui
- Cloudflare R2 (image storage, public bucket at r2.ycaptcha.xyspg.moe)
- Upstash Redis (rate limiting + captcha sessions)
- Deployed on Vercel

## Data Model

- **User** — managed by better-auth (do not modify schema.ts directly)
- **Site** — belongs to user, has siteKey (public) + secretKey (private)
- **ImageSet** — belongs to user (not site), reusable across sites. Acts as image pool for puzzles
- **Image** — belongs to imageSet. No tags. Just `{ id, imageSetId, url, name }`
- **Puzzle** — belongs to site, references imageSet. Has `correctImageIds` (jsonb array of all correct images), `correctCount` (integer, how many correct images to show per challenge), optional `incorrectImageIds` (null = random from pool), and `difficulty` (0-1 float, determines pass threshold via `Math.ceil(correctCount * difficulty)`)
- **CaptchaSession** — stored in Redis (not Postgres). Challenge sessions at `captcha:session:{token}`, verified sessions at `captcha:verified:{token}`. 5 min TTL, auto-expires

## API Flow

1. Widget loads `/widget/[siteKey]` in iframe
2. Widget calls `POST /api/v0/captcha/challenge` → creates Redis challenge session, returns proxy image URLs + session token
3. User selects images, widget calls `POST /api/v0/captcha/verify` → deletes challenge session, creates verified session in Redis, returns verification token
4. Parent page receives verification token via `postMessage`
5. Site owner's backend calls `POST /api/v0/captcha/siteverify` with verification token + secretKey → consumes (deletes) verified session, returns `{ success: true/false }`

## Verification Logic

- 9 images shown (3x3 grid, hardcoded)
- Each challenge randomly picks `correctCount` images from `correctImageIds` pool + fills rest from incorrect/random
- If all 9 selected → auto fail (anti-bot)
- Required correct selections = `Math.ceil(correctCount * difficulty)`
- Score = correctSelections - wrongSelections; must meet requiredCount to pass

## Auth Config

- better-auth handles all auth tables (user, session, account, verification, passkey)
- To update auth schema: run `bunx auth@latest generate`, copy output into `lib/db/schema.ts`
- App tables live in `lib/db/app-schema.ts`, never touched by auth generate
- drizzle.config.ts schema: `["./lib/db/schema.ts", "./lib/db/app-schema.ts"]`

## R2 Storage

- Bucket: `ycaptcha` at `r2.ycaptcha.xyspg.moe`
- Public access enabled
- File naming: `images/<nanoid>.jpg` (flat structure under images/ prefix)
- Upload flow: server action generates key → upload to R2 via S3 SDK → store public URL in db

## Server Action Conventions

- Actions live in `actions.ts` next to the page that uses them (e.g., `app/dashboard/sites/actions.ts`)
- Every action: auth first (`requireSession()`), then zod validation, then mutation scoped to `session.user.id`
- Return `ActionState` type: `{ errors?, message?, success? } | null`
- Always scope write queries with `eq(table.userId, session.user.id)` — never trust client-provided IDs alone
- Use `useActionState` on the client; for side effects (e.g., closing a sheet), wrap the action in the callback — never use `useEffect` to watch action state
- Rate limiting: per-route rate limits via `@upstash/ratelimit` (challenge: 20/min, verify: 10/min, siteverify: 100/min, image: 60/min, auth: 10/min)
- `getClientIP()` in `lib/utils.ts` for extracting client IP (Vercel `x-forwarded-for` based)

## Style Conventions

- Use `bun` not `npm`
- API routes under `/api/v0/`
- Use `env.VAR_NAME` from `lib/env.ts` (t3-env) instead of `process.env` for all env vars in app code. Exception: files like `drizzle.config.ts` that run outside the Next.js runtime and don't go through t3-env — use `process.env` there.
- run `bun run lint:fix` before committing

## Review Notes — Known False Positives

- **`process.env.X` in a `"use client"` component is NOT automatically broken.** Next.js's SWC compiler inlines `process.env.X` references in client code at build time, even for non-`NEXT_PUBLIC_` vars. The value gets baked into the client bundle as a string literal. SSR renders correctly, client-side re-renders (locale switch, state change, etc.) keep the correct value, and there is no hydration mismatch. Do NOT flag this as "will be `undefined` in the browser" or "latent footgun that breaks on re-render" — it has been empirically verified not to break. The only legitimate criticism is the t3-env convention (missing/misnamed var fails silently instead of raising a typed error at startup), which is a DX nit, not a bug. Also: `process` does not exist in the browser — never suggest typing `process.env.X` in a browser console to "verify" this.
- 
- In this project's CAPTCHA flow, the `origin` value sent to `/api/v0/captcha/challenge` is intentionally passed in the request body from the iframe widget to indicate the embedding site's origin. This is advisory site-context / anti-abuse metadata, not a hard security proof.
- Do not flag this as a security bypass by itself during code review. The real security boundary is the backend verification flow, especially `/api/v0/captcha/siteverify` with the private `secretKey`.
- Reviews should only raise a security finding here if the backend verification boundary is bypassed, omitted, or incorrectly trusted on the client.

# React useEffect Rules

## Rule: Never use `useEffect` directly

We ban direct `useEffect` calls. Use the patterns below instead.

### 1. Derive state inline — never sync state from state
```ts
// ❌ useEffect(() => setFiltered(items.filter(fn)), [items])
// ✅ const filtered = items.filter(fn)
```

### 2. Use data-fetching libraries (e.g. React Query) — never fetch in effects
```ts
// ❌ useEffect(() => { fetch(url).then(setData) }, [id])
// ✅ const { data } = useQuery(['key', id], () => fetchData(id))
```

### 3. Put logic in event handlers — never use state flags to trigger effects
```ts
// ❌ useEffect(() => { if (flag) doThing(); setFlag(false) }, [flag])
// ✅ <button onClick={() => doThing()}>
```

### 4. Use `useMountEffect()` for one-time external sync

For DOM integration, third-party widgets, or browser API subscriptions, use:
```ts
useMountEffect(() => {
  // setup
  return () => { /* cleanup */ }
})
```

Prefer conditional mounting (render the component only when preconditions are met) over guard clauses inside effects.

### 5. Reset components with `key` — never write effects that reset state on prop changes
```ts
// ❌ useEffect(() => { resetState(); load(id) }, [id])
// ✅ <MyComponent key={id} id={id} />
```

### Smell tests — stop and refactor if you see:

- `useEffect(() => setX(f(y)), [y])` → derive inline
- `fetch()` + `setState()` inside an effect → use query library
- State used as a flag to trigger an effect → move to event handler
- Effect whose only job is resetting on prop change → use `key`
